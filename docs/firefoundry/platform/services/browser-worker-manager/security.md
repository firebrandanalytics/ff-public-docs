# Browser Worker Manager — Credentials and Redaction

Agents that log into websites need credentials, but an LLM should never see, store, or echo a password. This page describes how BWM delivers secrets to a session, how the harness uses them without exposing them, and exactly what the redaction layer does and does not protect.

## Design Principle: Name the Secret, Never Send It

A consumer or agent refers to a credential only by its **key name** (`credentialKey` for `login`, `credentialRef` for `fill`). The harness resolves the key against a file mounted into its own pod and types the value itself. The secret value never appears in:

- the request the agent sends,
- the response the harness returns,
- the harness's log lines, including error paths.

This mirrors the approach of the [Notification Service](../notification-service/concepts.md), which stores only the *names* of credential environment variables rather than their values.

## How Credentials Reach a Session

```
Operator/app            Kubernetes              Session pod
────────────            ──────────              ───────────
credentials.json ──▶ Secret <credsSecretName> ──▶ /secrets/credentials.json (read-only)
                                                     │
Agent: {"credentialRef":"portal-password"} ─────────▶│ harness looks up key, types value
```

1. Create a Kubernetes Secret in the BWM namespace with a `credentials.json` key.
2. Pass its name as `credsSecretName` to `POST /sessions`. If you omit it, the manager uses `bwm-creds-<first 8 chars of sessionId>`, which in practice cannot be created in advance because the session ID is generated by the manager — so pass an explicit name.
3. The Secret is mounted read-only at `/secrets` (`SECRETS_PATH`). The mount is marked `optional`, so sessions without credentials start normally; credential verbs then return `412 credentials file not mounted`.
4. The file is re-read on every credential call, so the harness keeps no long-lived copy beyond what it needs for redaction (below).

Secrets are **never** passed as environment variables or through the manager API. The harness pod also runs with `automountServiceAccountToken: false`, so a compromised page cannot use the pod's identity against the Kubernetes API.

BWM does not create, rotate, or delete credential Secrets. Your application or operator is responsible for their lifecycle, including removing per-session Secrets after the session closes.

## Credential File Format

`credentials.json` is a JSON object mapping key names to entries. Each entry has a `mode`:

### `value` — for `fill` with `credentialRef`

```json
{
  "portal-username": { "mode": "value", "value": "<username>", "field": "text" },
  "portal-password": { "mode": "value", "value": "<password>", "field": "password" }
}
```

| Field | Required | Description |
|-------|----------|-------------|
| `value` | Yes | The secret to type |
| `field` | No | `"password"` or `"text"`. When `"password"`, the target must be an `<input type="password">`. |

### `formFill` — for `login` (scripted form login)

```json
{
  "portal": {
    "mode": "formFill",
    "loginUrl": "https://portal.example.com/login",
    "usernameSelector": "#username",
    "passwordSelector": "#password",
    "submitSelector": "button[type=submit]",
    "successSelector": "#account-dashboard",
    "username": "<username>",
    "password": "<password>"
  }
}
```

The harness navigates to `loginUrl`, fills username and password, clicks submit, and waits up to 10 s for `successSelector`. Success returns `{"ok":true,"mode":"formFill","url":…}`; a missing success selector returns `401`.

### `storageState` — for `login` (cookie restore)

```json
{
  "portal-cookies": {
    "mode": "storageState",
    "storageState": { "cookies": [ { "name": "session", "value": "<cookie>", "domain": "portal.example.com", "path": "/" } ] }
  }
}
```

Adds the listed cookies to the browser context. Only `cookies` is applied in this release; `origins` (local storage) is ignored, and nothing is ever written back to the file.

A `value` entry cannot be used with `login` (returns `404`), and `formFill`/`storageState` entries cannot be used with `fill` (returns `404`).

## Credential Fill Safeguards

A credential fill is not a blind write. For `POST /session/fill` with `credentialRef`:

1. **Ref required.** `credentialRef` must be paired with a `ref` from the current snapshot. Plain CSS selectors are rejected (`400 credentialRef requires ref`), because a selector cannot prove that the element being filled is the one the agent inspected.
2. **Same-node identity.** The ref is bound to the actual DOM node captured by the snapshot (a Playwright element handle). A page that replaces the field with an identical-looking impostor does not satisfy the ref.
3. **Current epoch.** Refs from an older snapshot, or taken before a navigation, are rejected with `409 stale-ref`.
4. **Revalidation immediately before typing.** The harness checks that the element is still attached, editable, an `<input>`, has the same `type` it had in the snapshot, and — for `field: "password"` — is `type="password"`. Any failure aborts **without typing** and returns `409 stale-ref` with `detail: "credential revalidation failed"`.

> **Note:** the type comparison uses the element's `type` *attribute*. An `<input>` with no explicit `type` attribute snapshots as `type: "text"` but has no attribute to compare against, so a credential fill into it fails revalidation. Target inputs with an explicit `type`, or use `login` with `formFill` for such forms.

Non-credential fills and clicks by ref only require the epoch and element to still be valid; they skip the type assertions.

## Redaction

The harness keeps an in-memory set of every secret it has injected in the session:

- each `value` resolved for a `credentialRef` fill (added as soon as it is resolved, before typing, so aborted fills are covered too),
- each `password` used by a `formFill` login.

Before any **page-derived** string leaves the harness — in a response body or a log line — every occurrence of those secrets is replaced with `[REDACTED]`. This covers:

| Verb | Redacted fields |
|------|-----------------|
| `navigate` | `title`, `url` |
| `snapshot` | `url`, each element's `name` |
| `extract` | `url`, `text` |
| `click` | `url` |
| `login` (`formFill`) | post-login `url`, page title in failure logs |
| `download` | `suggestedFilename` (response, log, and default blob name) |

Fill and login error responses use fixed messages and never include the underlying browser error, because browser automation errors can embed the text that was being typed.

The set is cleared when the harness receives `/shutdown`.

### What redaction is — and is not

Redaction is **hygiene, not a security boundary**. It protects against the common accident of a site reflecting a just-typed secret back into its title, URL, or visible text, and against secrets leaking into logs. It does not:

- redact the **username** used by a `formFill` login, or literal `value` fills — only values that came from the credentials file as secrets,
- redact cookies restored via `storageState`,
- detect transformed secrets (encoded, split, or partially masked),
- redact PDFs or downloaded files, which are stored as-is in Context Service,
- persist across sessions — each harness process has its own set.

The structural protections — secrets delivered by mounted Secret, key-name-only API, ref-bound revalidated fills, and no value field in snapshots — are the controls to rely on.

## Transport and Access Control

In this release the manager and harness APIs have **no authentication**, and the harness listens on the pod IP. Anything that can reach a harness pod on port 3000 can drive that browser, including filling the credentials mounted into it into any page it navigates to. The API never returns secret values, but a caller who controls the destination page could capture what is typed there. Treat BWM as an in-cluster service:

- Do not expose the manager or harness through an ingress.
- Restrict access to the BWM namespace with Kubernetes NetworkPolicies so only the consuming agent bundles can reach port 3000 and 3001 (the repository does not ship a NetworkPolicy).
- Limit who can create or read Secrets in the BWM namespace, since those Secrets hold site credentials.

See [Operations — Security](./operations.md#security) for deployment hardening.
