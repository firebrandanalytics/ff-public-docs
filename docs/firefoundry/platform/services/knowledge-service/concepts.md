# Knowledge Service — Concepts

This page explains the mental model behind the Knowledge Service: what a knowledge base and a document are, where they live in the entity graph, how ingestion moves a document through its lifecycle, and how the service relates to the RAG agent bundle.

## The Big Picture

A FireFoundry knowledge base is not a separate vector store. It is a **partition of the entity graph** that holds documents and the rich subgraph the RAG agent bundle builds from them (sections, pages, chunks, tables, figures, with embeddings and summaries). The Knowledge Service is the catalog and control plane in front of that partition:

```
 Your app                Knowledge Service              RAG agent bundle
 --------                -----------------              ----------------
 create KB      ───────▶ create partition + KB entity
 register doc   ───────▶ create Document (registered)
 trigger ingest ───────▶ mark queued, forward ────────▶ extract, chunk, embed,
                                                        build subgraph
                          mark complete / failed ◀───── callback
 list / filter  ───────▶ read Document entities
 navigate       ───────▶ read sections / pages
 ask questions  ─────────────────────────────────────▶ /api/rag-query
```

The service holds no state of its own — no database, no queue. Everything it reports is read from, and everything it changes is written to, the [Entity Service](../entity-service/README.md). That makes it stateless and safe to run with multiple replicas.

## Core Domain Objects

### Knowledge Base

A knowledge base (KB) is a named collection of documents. Creating one does two things in the entity graph:

1. **Creates a partition** whose name is the new KB id (a server-issued UUID). All of the KB's documents and ingestion output will live in this partition.
2. **Creates a `KnowledgeBase` entity** in the shared `system` partition, with the same id, holding the KB's `name` and `description`. This is the KB index that `GET /api/kb` lists.

| Field | Description |
|---|---|
| `id` | Server-issued UUID. Also the partition name and the URL path segment. |
| `name` | Display name (required, non-empty) |
| `description` | Optional free-text description |
| `createdAt` / `updatedAt` | ISO-8601 timestamps from the entity graph |

KB ids are always generated by the service, so partition-name collisions cannot happen.

### Document

A document is a registration of one source file into a KB. It is stored as a `Document` entity inside the KB's partition.

| Field | Description |
|---|---|
| `id` | Server-issued UUID |
| `kbId` | The owning KB |
| `metadata` | Descriptive metadata (see below) |
| `blobPath` | Reference to where the raw file is stored (for example a working-memory path). The Knowledge Service never reads the file; it passes this reference to the RAG agent bundle. |
| `status` | Ingestion status (see [lifecycle](#document-lifecycle)) |
| `jobId` | Ingestion job id, set when ingestion is triggered |
| `entityCount` / `edgeCount` | Populated from the completion callback |
| `error` | Populated from a failure callback; cleared on a later non-failed status |
| `uploadedAt` / `updatedAt` | ISO-8601 timestamps |

**Document metadata** supplied at registration:

| Field | Required | Notes |
|---|---|---|
| `title` | yes | Also used as the entity's name |
| `mimeType` | yes | e.g. `application/pdf` |
| `authorNames` | no | Array of strings |
| `sourceUri` | no | Where the document originally came from |
| `pageCount`, `fileSize` | no | Non-negative integers |
| `publishedDate` | no | Free-form string |
| `issuer` | no | Financial-filing metadata (snake_case by design) |
| `fiscal_year` | no | Non-negative integer |
| `fiscal_period` | no | One of `Q1`, `Q2`, `Q3`, `Q4`, `FY` |
| `document_type` | no | e.g. `10-K` |

The four financial-filing fields are **registration-canonical**: they are stored on the document as soon as it is registered (so list filters match it immediately, before ingestion) and are forwarded to the RAG agent bundle as `config.documentMetadataOverride` when ingestion is triggered, so the bundle stamps the same values onto the metadata it writes. After ingestion, the RAG agent bundle enriches the document's `metadata` with additional fields of its own (for example `ingestion_version`, `language`, page and table counts); these are returned as-is by the document endpoints.

### Ingestion Subgraph

When the RAG agent bundle ingests a document it creates structural entities in the KB partition, linked by structural edges:

| Entity | Meaning |
|---|---|
| `Section` | A heading-delimited part of the document, nested by depth |
| `Page` | A physical page, with an optional printed page label |
| `Chunk` | A retrievable span of text with embeddings |
| `Table`, `Figure` | Visual elements anchored to pages |

| Edge | Meaning |
|---|---|
| `CONTAINS` | Structural backbone: Document → Page / Section, Section → Section / Chunk / Table / Figure |
| `PRECEDES` | Reading order between siblings |
| `SPANS` | A section, chunk, table, or figure covers one or more pages |

The Knowledge Service does not create any of these. It reads them to serve the [structural views](#structural-views) and deletes them during a [cascade delete](#deletion-semantics). See the [RAG Agent Bundle](../../system-agents/rag-agent.md) page for how the subgraph is built.

## Partition Layout

```
system partition                     KB partition  (name = kbId)
+--------------------------+         +------------------------------------------+
| KnowledgeBase  (id=kbId) |  ....>  | Document ── CONTAINS ──▶ Section ──▶ Chunk |
| KnowledgeBase  ...       |         |    │                        │            |
+--------------------------+         |    └─ CONTAINS ─▶ Page ◀── SPANS ─┘       |
                                     |                   Table / Figure         |
                                     +------------------------------------------+
```

Every document read goes through a client scoped to the KB's partition, so a document id that exists in a different KB is simply "not found". The service authors its own entities under a stable identity (`KNOWLEDGE_SERVICE_BUNDLE_ID` and `APPLICATION_ID`), which lets entity-graph tooling recognize knowledge-base records.

## Document Lifecycle

Every document moves through this status flow:

```
registered -> queued -> in-progress -> complete
                                    \-> failed
```

| Status | Set by | Meaning |
|---|---|---|
| `registered` | Register endpoint | Document metadata exists; ingestion has not been triggered |
| `queued` | Trigger endpoint | The RAG agent bundle was reached and the request is in flight; a `jobId` is recorded |
| `in-progress` | — | Reserved for progress updates from the bundle during long ingestions. Version 0.2.0 does not set this state; a document stays `queued` until the callback arrives. |
| `complete` | Callback | The bundle reported success; `entityCount` and `edgeCount` are populated |
| `failed` | Callback | The bundle reported failure; `error` is populated and the document can be re-triggered |

Rules:

- **Re-triggering** is allowed from `registered` or `failed`. Triggering a document that is `queued`, `in-progress`, or `complete` returns `409` with code `ingestion_in_flight`.
- **Status is not editable** through `PUT /api/kb/{kbId}/documents/{docId}`; only the trigger and callback move it.
- **If the bundle cannot be reached** (connection refused, DNS failure, or an immediate non-2xx response), the trigger returns `502` and the document keeps its previous status, so the caller can simply retry.
- **Callbacks are idempotent.** Delivering the same callback twice produces the same document state. A callback whose `jobId` differs from the recorded one is still applied (the callback is the source of truth) and a warning is logged — this typically means the document was re-triggered.
- **Merge, don't overwrite.** Status updates merge into the stored document data, so metadata and any fields the RAG agent bundle wrote during ingestion are preserved.
- **No sweeper.** If a callback never arrives, the document remains `queued`. Monitor for long-lived `queued` documents (see [Operations](./operations.md#troubleshooting)).

## How Ingestion Is Triggered

When you call `POST /api/kb/{kbId}/documents/{docId}/ingest`, the service:

1. Loads the document and checks its status (404 if missing, 409 if already in flight or complete).
2. Allocates a new `jobId` (UUID).
3. POSTs `{ kbId, documentId, blobPath, config: { jobId, documentMetadataOverride? } }` to `${RAG_AGENT_BUNDLE_URL}/api/kb-ingest`.
4. Waits for the bundle's response for at most `RAG_BUNDLE_TIMEOUT_MS`. A 2xx response, or the window elapsing while the request is still pending, counts as "fired"; the request keeps running in the background. A connection failure or non-2xx response inside the window counts as a failure (502).
5. Marks the document `queued` with the `jobId` and returns `202` with `{ jobId, status: "queued", message }`.

The RAG agent bundle then reports the outcome by calling `POST /api/kb/ingestion-callback` with `{ jobId, documentId, kbId, status: "complete" | "failed", entityCount?, edgeCount?, error? }`. The bundle must be configured with the Knowledge Service's URL to do this. Application code does not normally call the callback endpoint directly.

## Structural Views

Once a document has been ingested by the RAG agent bundle's structured (v2) pipeline, three read endpoints let an agent explore it without running a query:

- **Capabilities** — `GET /api/kb/{kbId}/documents/{docId}/capabilities` returns a summary: counts of pages, sections, chunks, tables, and figures; section-depth histogram; page-label kinds; structural edge counts; and flags such as `is_navigable_by_section`, `is_addressable_by_label`, and `supports_table_query`. Documents without a structured ingestion (no `ingestion_version`, or a `v1…` version) return `{ "ingestion_version": "v1", "capabilities": null }`, meaning they are searchable but not structurally addressable. Responses are cached per replica for `CAPABILITIES_CACHE_TTL_SECONDS` (default 60) and invalidated on delete.
- **Sections** — `GET /api/kb/{kbId}/sections/{sectionId}` returns a section with its full subtree: child sections (recursively), chunks, and the pages it spans.
- **Pages** — `GET /api/kb/{kbId}/pages/{pageId}` returns one page with its text, the chunks and sections that span it, and any tables or figures on it.

### Page addressing

`pageId` is deliberately polymorphic:

| Input | Interpreted as |
|---|---|
| A UUID | The Page entity id (always unambiguous) |
| A non-negative integer, e.g. `0`, `42` | Both a physical page index (0-based) **and** a printed label; results are merged |
| Anything else, e.g. `iii`, `A-3` | A printed page label |

If the reference matches exactly one page you get `200`. If it matches several (for example physical page `42` and a different page printed as "42", or two appendices both labeled `A-1`), you get `409` with a disambiguation body listing each match's `id`, `physical_page_index`, and `page_label`, so you can retry with the id. No match returns `404` with code `page_not_found`.

Note that page lookups are scoped to the **KB**, not to a single document.

## Deletion Semantics

Deletes are **hard deletes** (cascade), not archives:

- **Delete a document** — the service walks the document's `CONTAINS` subgraph, deletes every child (sections, pages, chunks, tables, figures) and then the document itself through the Entity Service admin API. Edges and vector-similarity rows are removed by the database's cascading foreign keys. Children are deleted first and the document last, so an interrupted delete leaves the document in place and can be safely retried. Transient database deadlocks are retried automatically with backoff.
- **Delete a knowledge base** — cascade-deletes every document in the partition, sweeps any leftover nodes, and finally deletes the `KnowledgeBase` entity from the `system` partition. The now-empty partition itself remains; this is harmless.

Hard deletion requires the Entity Service admin API. In environments where the Entity Service enforces an admin key, the Knowledge Service must be configured with `ENTITY_SERVICE_ADMIN_API_KEY`, otherwise deletes fail with `500` (see [Operations](./operations.md#security)).

## Interaction With Other Services

| Service | Direction | Purpose |
|---|---|---|
| [Entity Service](../entity-service/README.md) | Knowledge Service → | Partition creation, node CRUD, scoped search, edge reads, admin hard-delete |
| [RAG agent bundle](../../system-agents/rag-agent.md) | Knowledge Service → | `POST /api/kb-ingest` to start ingestion |
| [RAG agent bundle](../../system-agents/rag-agent.md) | → Knowledge Service | `POST /api/kb/ingestion-callback` to report completion; the bundle's document-listing tool can also call the filtered list endpoint |
| [Context Service](../context-service/README.md) | indirect | Typical home of the file referenced by `blobPath`; read by the RAG agent bundle, not by the Knowledge Service |
| Application / agent bundles | → Knowledge Service | Catalog management and structural navigation; questions go to the RAG agent bundle's `/api/rag-query` |

## Limits and Known Constraints

- `GET /api/kb` and unfiltered `GET /api/kb/{kbId}/documents` return at most **200** items; `total` is the uncapped count, so `total > data.length` tells you the list was truncated. Use filter parameters (which enable `page`/`size` pagination) for large KBs.
- Filtered listing evaluates filters against the document's stored `metadata`; documents that do not carry a field (for example a v1 ingestion without `issuer`) will not match a filter on it.
- Capability edge counts for `PRECEDES` and `SPANS` are upper-bound estimates; `edges.counts_are_exact` tells you which counts are exact.
- There is no upload endpoint: store the file first and pass its `blobPath` at registration.
- There is no in-service authentication in 0.2.0; see [Operations](./operations.md#security).
