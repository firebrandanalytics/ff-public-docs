# Knowledge Service — Concepts

This page explains the model an app builder works with: knowledge bases, documents, the ingestion lifecycle, structural navigation, and deletion — and how to design an app around them.

## The Big Picture

```
 Your app                    Knowledge Service            RAG agent bundle
 --------                    -----------------            ----------------
 store file in working memory
 create KB          ───────▶ returns kbId
 register doc       ───────▶ returns docId (registered)
 trigger ingestion  ───────▶ returns 202 (queued) ──────▶ extract, chunk, embed
 poll document      ───────▶ queued … complete | failed ◀── reports result
 browse structure   ───────▶ capabilities, sections, pages
 ask questions      ────────────────────────────────────▶ POST /api/rag-query { kbIds }
```

A knowledge base is not a separate vector store. Its content (documents and everything ingested from them) lives in the FireFoundry entity graph, so the same data that answers RAG queries can also be navigated section by section and page by page.

## Knowledge Base

A knowledge base (KB) is a named collection of documents. It is the unit you scope queries to: `/api/rag-query` takes a list of `kbIds`.

| Field | Description |
|---|---|
| `id` | Server-issued UUID. Use it in every document, navigation, and query call. |
| `name` | Display name (required, non-empty). Names are not unique. |
| `description` | Optional free text |
| `createdAt` / `updatedAt` | ISO-8601 timestamps |

KB ids are always generated by the service. `GET /api/kb` lists every KB in the environment (not just your app's), so **store the ids of the KBs your app creates** — in your app's own entities or configuration — rather than finding them by name.

## Document

A document is the registration of one stored file into a KB.

| Field | Description |
|---|---|
| `id` | Server-issued UUID |
| `kbId` | The owning KB |
| `metadata` | Descriptive metadata you supply (see below); enriched by ingestion |
| `blobPath` | Reference to the stored file. The RAG agent bundle reads the file from here; the Knowledge Service never uploads or reads it. |
| `status` | Ingestion status (see [lifecycle](#document-lifecycle)) |
| `jobId` | Ingestion job id, set when ingestion is triggered |
| `entityCount` / `edgeCount` | Size of what ingestion produced, set on completion |
| `error` | Failure message, set when ingestion fails |
| `uploadedAt` / `updatedAt` | ISO-8601 timestamps |

**Metadata you supply at registration:**

| Field | Required | Notes |
|---|---|---|
| `title` | yes | |
| `mimeType` | yes | e.g. `application/pdf` |
| `authorNames` | no | Array of strings |
| `sourceUri` | no | Where the document originally came from |
| `pageCount`, `fileSize` | no | Non-negative integers |
| `publishedDate` | no | Free-form string |
| `issuer` | no | Financial-filing fields (snake_case by design) |
| `fiscal_year` | no | Non-negative integer |
| `fiscal_period` | no | `Q1`, `Q2`, `Q3`, `Q4`, or `FY` |
| `document_type` | no | e.g. `10-K` |

The four financial-filing fields are stored at registration, so list filters match them immediately, and they are passed to ingestion so the ingested document carries the same values. After ingestion the document's `metadata` also contains fields written by the RAG agent bundle (for example `ingestion_version`, `language`, page and table counts); several list filters target those fields.

There is no upload endpoint. Store the file first — typically in working memory via the [Context Service](../context-service/README.md) — and pass its path as `blobPath`.

## Document Lifecycle

```
registered ──trigger──▶ queued ──▶ complete
                                └─▶ failed ──trigger again──▶ queued …
```

| Status | Meaning | What your app does |
|---|---|---|
| `registered` | Metadata exists; ingestion not started | Trigger ingestion |
| `queued` | Ingestion accepted and running | Keep polling |
| `in-progress` | Reserved for future progress reporting; not set in 0.2.0 | Treat like `queued` |
| `complete` | Ingested; `entityCount`/`edgeCount` set | Document is queryable and navigable |
| `failed` | Ingestion failed; `error` set | Show the error; fix the cause; trigger again |

Rules that affect your app:

- **Ingestion is asynchronous.** The trigger returns `202` with `status: "queued"` once the RAG agent bundle has accepted the work. Poll `GET /api/kb/{kbId}/documents/{docId}` until `status` is `complete` or `failed`. Ingestion of a large document can take minutes; use a polling interval of a few seconds and an overall timeout that suits your document sizes.
- **Retry on 502.** If the RAG agent bundle cannot be reached, the trigger returns `502` and the document keeps its previous status — retry the same call.
- **Triggering is allowed only from `registered` or `failed`.** Triggering a `queued`, `in-progress`, or `complete` document returns `409 ingestion_in_flight`.
- **Re-ingesting a completed document** means deleting it and registering it again.
- **Status is not editable** through `PUT`; only ingestion moves it.
- **A document that stays `queued`** far longer than your expected ingestion time did not report back. Delete and re-register it, and see [troubleshooting](./operations.md#troubleshooting).

## What Ingestion Produces

When a document is ingested by the RAG agent bundle's structured pipeline, it is broken into:

| Element | Meaning |
|---|---|
| Section | A heading-delimited part of the document, nested by depth |
| Page | A physical page, with an optional printed page label |
| Chunk | A retrievable span of text with embeddings — what `/api/rag-query` searches |
| Table, Figure | Visual elements anchored to pages |

Sections contain child sections, chunks, tables, and figures; sections and chunks record the pages they span. The Knowledge Service exposes this structure read-only through the navigation endpoints below. See the [RAG Agent Bundle](../../system-agents/rag-agent.md) for ingestion options.

## Structural Navigation

Once a document is `complete`, three read endpoints let a user interface or an agent explore it without running a semantic query:

- **Capabilities** — `GET /api/kb/{kbId}/documents/{docId}/capabilities` summarizes what the document offers: counts of pages, sections, chunks, tables, and figures; section-depth histogram; page-label kinds; and flags such as `is_navigable_by_section`, `is_addressable_by_label`, and `supports_table_query`. A document without structured ingestion returns `{ "ingestion_version": "v1", "capabilities": null }` — it can still be queried through the RAG agent bundle, but section and page lookups find nothing for it. Capability responses may be up to about a minute stale after a document is re-ingested.
- **Sections** — `GET /api/kb/{kbId}/sections/{sectionId}` returns a section with its full subtree: child sections (recursively), chunks, and the pages it spans.
- **Pages** — `GET /api/kb/{kbId}/pages/{pageId}` returns one page with its text, the chunks and sections that span it, and any tables or figures on it.

Use the capability flags to decide which navigation to offer: a document with `is_navigable_by_section: false` has no useful outline, and one with `is_addressable_by_label: false` has no printed page labels.

### Page addressing

`pageId` accepts three kinds of reference:

| Input | Interpreted as |
|---|---|
| A UUID | The page's id (always unambiguous) |
| A non-negative integer, e.g. `0`, `42` | Both a 0-based physical page index **and** a printed label; results are merged |
| Anything else, e.g. `iii`, `A-3` | A printed page label |

One match returns `200`. Several matches (for example physical page `42` and a different page printed as "42", or two appendices both labeled `A-1`) return `409` with a list of candidates (`id`, `physical_page_index`, `page_label`) so your app can pick one and retry with its id. No match returns `404 page_not_found`.

Page and section lookups are scoped to the **KB**, not to a single document. If a KB holds many documents, a label such as `1` is likely to be ambiguous — prefer page ids taken from a section or page response (each page response carries its `document_id`), and when you do get a `409`, fetch the candidates by id to see which document each belongs to.

## Deletion

Deletes are permanent:

- **Deleting a document** removes it and everything ingested from it (sections, pages, chunks, tables, figures, embeddings). It no longer appears in query results.
- **Deleting a KB** does the same for every document in it, then removes the KB.

Deletes of large documents or KBs can take a while. If one fails part-way (for example with `503`), repeating the same `DELETE` is safe.

## Designing Apps Around Knowledge Bases

### Document Q&A

The most common shape: users upload documents and ask questions about them.

1. On first use, create a KB for the app (or per workspace — see below) and store its id.
2. When a user uploads a file, store it in working memory, register it with a title and MIME type, and trigger ingestion.
3. Show the document as "processing" while you poll; show `error` if it fails, with a retry button that triggers again.
4. For each question, call `/api/rag-query` with the KB id(s) and put the returned `context` into your bot's prompt. Use `sources` (document id, chunk id, title, relevance) to render citations.
5. Let users open a cited document and browse it with the navigation endpoints (capabilities, sections, pages). Note that there is no endpoint to look up a single chunk by id; page and section responses list the chunks they contain.

### One KB or many?

A query is scoped by the list of `kbIds` you pass, so the KB is your isolation and scoping unit:

| Layout | When to use it | Trade-off |
|---|---|---|
| One KB per app | Shared corpus for all users (product docs, policy manual) | Simplest; every query sees every document |
| One KB per tenant, workspace, or project | Users must only see their own documents | Your app keeps the mapping from tenant to KB id; delete a tenant's content by deleting its KB |
| Several topical KBs | Different corpora queried in different situations | Choose which `kbIds` to pass per question; a query can span several KBs |

The Knowledge Service has no per-caller access control in 0.2.0, so isolation between tenants comes from your app only ever passing the right KB ids.

### Filtered research over a corpus

For corpora with structured metadata (for example financial filings), register documents with `issuer`, `fiscal_year`, `fiscal_period`, and `document_type`. Your app or agent can then list the relevant documents with server-side filters (`issuer=ACME&fiscal_year_min=2023&document_type=10-K`) before asking questions, show the user which documents are in scope, and pass metadata filters to `/api/rag-query`.

### Navigation-first agents

For long, well-structured documents (specifications, contracts, manuals), an agent can read the capability summary, walk sections, and fetch specific pages ("what does section 4.2 say?", "show page iii") instead of relying only on semantic search. Combine both: use `/api/rag-query` to find where something is, then fetch the surrounding section for full context.

## Limits and Behavior to Design Around

- Unfiltered `GET /api/kb` and `GET /api/kb/{kbId}/documents` return at most **200** items; `total` is the uncapped count, so `total > data.length` means the list was truncated. Add any filter parameter to get `page`/`size` pagination.
- Filters match against the document's stored `metadata`; documents that do not carry a field do not match a filter on it.
- Capability edge counts for `precedes` and `spans` may be estimates; `edges.counts_are_exact` tells you which are exact.
- Request bodies are limited to 10 MB (metadata only — files are never sent to this service).
- No upload endpoint and no in-service authentication in 0.2.0.
